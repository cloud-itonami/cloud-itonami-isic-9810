各行は「resume で実際に渡した承認者 ID の文字列が、store が残したどこに現れるか」を走査した結果。この repo の挙動を決め打ちしていないので、store の保持内容が変われば次のビルドで表も変わる。

観測: 帰属は :payload にのみ残る

4 件のコミット済みレコードで、承認者 ID は :payload には在るが :value には無い。hhproductionops.operation の commit-record は両フィールドを同じ提案 :value から作り、承認ノードだけが :payload を上書きするため、同一レコードの 2 つの見え方が食い違う。:value を読む下流は承認者を失う。

観測: 承認者は永続台帳に一切現れない

4 件の承認済みシナリオすべてで、承認者 ID は台帳のどのファクトにも現れなかった。「誰が承認したか」は監査台帳への query では答えられず、コミット済みレコードの :payload からしか復元できない。

9. 開示 — 本ビルドで観測した欠落 (このタスクでは修正していない)

レンダリング作業の中で governor を黙って書き換えることはしない。観測した事実のみを掲示する。

承認ファクトが監査台帳に到達しない

:approval-requested と :approval-granted は hhproductionops.operation のグラフ内で生成されるが、:commit ノードは commit-fact のみを、:hold ノードは :governor-hold/:approval-rejected のみを台帳へ書く。結果として、本実行の台帳 16 ファクト中に承認関連ファクトは 0 件 (上記 6 節)。

高額支援のエスカレート理由が :always-escalate と表示される

S05 (estimated-cost 900.0 > support-cost-threshold 250.0) の :approval-requested は :reason :always-escalate を出すが、:coordinate-programme-support は governor/always-escalate-ops ([:flag-food-security-concern]) の要素ではない。operation の :decide ノードが :high-stakes? を 一律 :always-escalate に写像しているため、「常時エスカレートする op」と「金額しきい値で今回だけエスカレートした提案」が 理由コードでは区別できない。実際の識別子は verdict の :high-stakes? と op 自体。

store に承認専用の書き込み関数は無い

hhproductionops.store/Store プロトコルは commit-record! と append-ledger! のみを持ち、承認を記録する関数を持たない。承認はグラフの interrupt-before / resume として実在するが、store 側には承認という概念の座席が無い。
